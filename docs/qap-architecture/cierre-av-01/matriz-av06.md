## Plataforma × distribución × modalidad

**Leyenda.** Cada entrada se lee **visible / headless**. **P** = binario de Playwright documentado, por ensayar en QAP. **S** = canal estable de sistema documentado, sujeto a versión, instalación, política y doctor. **E** = ruta de emulación x64 por investigar, con métricas separadas. **D** = duda de proveedor/binario o canal que requiere prueba previa. **—** = modalidad inaplicable a la distribución. Linux representa un sistema gráfico en visible, con servidor de pantalla y permisos válidos. Las filas Linux propuestas se materializan en el expediente separadamente para Ubuntu 24.04 LTS y Debian 13, conservando versión exacta de kernel, bibliotecas, display y sandbox.

Windows ARM64 debe registrar arquitectura de Node, proceso navegador y helpers; un registro Win64 de PW no acredita un binario ARM64 nativo. En Linux ARM64, para Chromium y Shell el registro 1.62.1 usa builds de Playwright y 1.63.0 referencia Chrome for Testing. Para Chrome estable Google documenta paquetes ARM64, con arranque y detección del canal pendientes. El índice oficial de Edge estable ARM64 consultado tiene Packages vacío; comprobar proveedor y canal como condición de viabilidad. Safari de sistema, Firefox de sistema y Chromium de distribución Linux son comparadores independientes si se propone otro backend, con pruebas propias. WSL, contenedores, CI, emulación, otras versiones de SO y 32 bits requieren perfil y evidencia específicos. Una celda faltante de alcance obligatorio conserva el bloqueo y se escala al propietario. ## Capacidades por celda

Cruzar cada modalidad aplicable de la matriz con estas filas. Para el expediente instalado marcar por eje **acreditada**, **fallida**, **bloqueada**, **pendiente** o **inaplicable con razón**. En esta auditoría todas las combinaciones aplicables quedan pendientes de acreditación de QAP. Si el proveedor declara una capacidad de API, se requiere prueba integrada bajo configuración y permisos reales del fixture.

| Distribución y modo | UI y gráficos | PNG/WebM genuino y backend candidato | Evidencia privada y portabilidad |
|---|---|---|---|
| Chromium Shell headless | Preflight de SPA/CSS/fuentes/GPU por SO/CPU. Solo headless. | PNG y WebM por API de PW como candidato, con prueba de raster, movimiento, paso/seek y presupuesto. | Primera prueba del candidato C bajo EXP-06a; aplicar A si C falla y repetir garantías. |
| Chromium completo visible / headless nuevo | Dos celdas. Comparar efectos de sesión gráfica, GPU, compositor, foco y viewport. | PNG y WebM de contenido por modo. Verificar popup, OOPIF y tiempos. Video separado de ventana visible. | Misma ruta prioritaria y compuertas. Prueba de captura y visor por celda. |
| Chrome / Edge estable visible / headless nuevo | Probar por canal y políticas de red, proxy, CA, permisos, actualización, codecs y SSO. | PNG y WebM de contenido como candidatos, con verificación independiente por canal/modo. | La compatibilidad del motor Chromium orienta la ruta C/A y no se transfiere sin pruebas. |
| Firefox de Playwright visible / headless | Probar localizadores, frames, auth, archivos, permisos/red y layout efectivos. | PNG y grabación de contexto candidata; verificar WebM generado, reproducción y API soportada por revisión. | CDP Chromium queda fuera de esta ruta. Identificar backend protegido equivalente con pruebas previas; mantener capacidad pendiente donde falte. |
| WebKit de Playwright visible / headless | Probar variante por SO, librerías, fuentes, codecs y dependencias nativas. | PNG y grabación de contexto candidata; verificar WebM generado y reproducción en navegadores objetivo y traslado entre plataformas. | Identificar backend protegido equivalente y verificar prevención/custodia. Menor alcance requiere decisión del propietario. |

En cada fila se evalúa autenticación de prueba, red autorizada, UI con testigo, captura por paso, accesibilidad automática y teclado, publicación canónica, reproducción y export. Diagnóstico registra distribución consumida y codec/visor concretos. Capturar WebM de contenido no acredita escritorio ni diálogos OS. La referencia de AR-27 conserva controles de primer cuadro y la independencia entre captar, acceder, retener y exportar; un resultado histórico Chromium/Windows solo aporta antecedente. API Screencast aparece desde v1.59, y opciones publicadas después de estas versiones, como fps y style en 1.64 según documentación, quedan fuera de las capacidades presumibles del lock.
